# frontend/

Next.js 16 (App Router) + TypeScript estricto (`strict`, `noUncheckedIndexedAccess`), Tailwind 4, shadcn/ui, TanStack Query y next-intl (`es-PE`). Versiones: ADR-012 §4.1.

## Uso

Requiere Node 24.21.0 (`.nvmrc`) y pnpm 12.8.1 (`packageManager`).

```bash
cd frontend
pnpm install --frozen-lockfile
BACKEND_ORIGIN=http://127.0.0.1:8000 pnpm dev   # /api y /ws → Django (same-origin, ADR-003)
```

| Script                              | Qué hace                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------ |
| `pnpm format:check` / `pnpm format` | Prettier (con orden de clases de Tailwind)                                     |
| `pnpm lint`                         | ESLint (Next + `react/no-danger`, sin `innerHTML`), sin warnings               |
| `pnpm typecheck`                    | `tsc --noEmit`                                                                 |
| `pnpm test --run`                   | Vitest + Testing Library                                                       |
| `pnpm build`                        | Build de producción (`BACKEND_ORIGIN` se fija en el build)                     |
| `pnpm api:generate`                 | orval: `../backend/openapi/schema.yaml` → `src/lib/api/` (generado, no editar) |

## Estructura

- `src/app/`: `/login` y `/o` son el acceso (ver «Acceso»); `/recuperar` pide un enlace de recuperación de contraseña y `/restablecer` la cambia con él (ver «Recuperar la contraseña»); `/o/[orgSlug]` es el workspace de una organización (ver «Workspace de una organización»); `/` lleva a `/o`; `/status` muestra el estado del backend (consultado desde el servidor); `/demo` es la demo visual (ver abajo).
- `src/components/app-shell/`: guardia de la organización (`TenantGate`), barra lateral, barra superior y workspace, con el lenguaje del Figma GOOD DOGGY. El workspace necesita JavaScript: hasta que la API responde, el HTML solo lleva el aviso de carga. En pantallas pequeñas la barra lateral va en un menú (`<dialog>` nativo, con su botón de cerrar). WCAG AA, `prefers-reduced-motion`.
- `src/components/auth/`: formulario de acceso, lista de organizaciones y los dos formularios de la recuperación de contraseña.
- `src/components/ui/`: componentes shadcn/ui y primitivas de formulario (`TextField`).
- `src/lib/api/`: cliente generado por orval. **Nunca** tipos de API a mano: si cambia el contrato, regenerar el schema del backend y después ejecutar `pnpm api:generate`.
- `src/lib/http.ts`: el único `fetch` hacia la API (ver «Cliente de API»).
- `src/components/demo/`: landing y workspace de la demo visual, con sus datos ficticios.
- `messages/es-PE.json`: catálogo i18n.

La primera pantalla de gestión es «Miembros» (ver «Miembros»). Las pantallas reales se construyen en `/o/[orgSlug]`, sobre la API y el cliente generado, con el Figma GOOD DOGGY como referencia visual ([AGENTS.md](../AGENTS.md) §11).

## Cliente de API (F2-08A, ADR-014)

orval genera las funciones y los hooks; todos llaman a `apiFetch` (`src/lib/http.ts`), el único `fetch` hacia `/api/`:

- Mismo origen y cookies del mismo origen. La sesión es una cookie `HttpOnly`: el código no la ve ni guarda nada de ella en `localStorage`.
- Solo para el navegador (URL relativa y `document.cookie`): un Server Component no lo llama. Si una página del servidor necesita datos del usuario, delega en un componente cliente.
- En `POST`, `PUT`, `PATCH` y `DELETE` copia la cookie `csrftoken` en la cabecera `X-CSRFToken`. Si la cookie no existe todavía, la pide antes; si no la consigue, no envía la escritura y el error es el de esa petición. Una escritura a otro origen se rechaza sin enviarla.
- Una respuesta de error se convierte en `ApiError` con `status`, `code`, `fields` y `retryAfter` (segundos enteros), y así se tipa el `error` de cada hook generado. La red caída, también a mitad de una respuesta, es `NETWORK_ERROR` (`status` 0). Un 2xx que no es JSON es `INTERNAL_ERROR`. El texto de la respuesta nunca se muestra.
- Una descarga del contrato (un 2xx `text/csv`: la plantilla y el informe de errores de una importación) llega como `Blob`; cualquier otro 2xx que no es JSON sigue siendo `INTERNAL_ERROR`.
- Cancelación: TanStack Query cancela con su propia señal (cambio de `queryKey`, desmontaje, `cancelQueries`) y eso no llega a la pantalla como error. Con una señal propia, un `abort()` sin motivo se relanza como `AbortError`; un motivo propio o `AbortSignal.timeout` llegan como `NETWORK_ERROR`.
- `apiErrorKey(error)` (`src/lib/api-errors.ts`) da la clave del mensaje en `messages/es-PE.json` → `errors.api`. Un `code` sin mensaje propio usa el genérico.
- TanStack Query no repite una respuesta 4xx ni una escritura; reintenta una vez lo que no llegó o falló en el servidor.

## Acceso (F2-08B, ADR-003 §1–3)

- **`/login`:** correo y contraseña contra `POST /api/v1/auth/login/`. La sesión es la cookie `HttpOnly` que pone la API; el formulario no guarda nada. Quien ya tiene sesión pasa al destino en cuanto la API lo confirma: hasta entonces ve el formulario normal; desde la confirmación y hasta que la navegación termina, el botón queda ocupado. El formulario declara `method="post"`: un envío antes de que cargue el JavaScript no pone la contraseña en la URL.
- **Accesos de prueba (F2-117, ADR-026 §5):** bajo el formulario, `TestAccounts` pide `GET /api/v1/auth/test-accounts/` y solo se pinta si responde con cuentas: con el interruptor del backend apagado (siempre en `production`) la ruta da 404 y no queda nada en la página; no hay interruptor en el frontend. Cada cuenta enseña su rol y su correo; elegirla escribe el correo y lleva el foco a la contraseña, que no se completa nunca: el acceso sigue siendo el normal (contraseña, límites, CSRF, segundo paso). Nada se guarda en el navegador.
- **Segundo paso (F2-107, ADR-023 §5):** si la cuenta tiene segundo factor, la API responde 202 `mfa_required` a la contraseña correcta y todavía no hay sesión. `/login` cambia al paso del código en la misma tarjeta, sin navegar (`LoginSecondStep`): un campo para el código de la aplicación de autenticación o uno de respaldo, contra `POST /api/v1/auth/login/mfa/`. Con un código válido entra como tras la contraseña. Un código que no vale se dice junto al campo y deja probar otro. Un 401 `MFA_LOGIN_NOT_STARTED` (el acceso a medias caducó a los 5 minutos o dejó de valer) vuelve al paso de la contraseña con su aviso, el correo ya escrito y el foco en la contraseña. `RATE_LIMITED` dice la espera, en minutos o, pasada una hora, en horas (el tope de códigos de la cuenta llega a un día). **Un solo envío:** con un código en vuelo no sale nada más con la cookie del acceso a medias, porque una petición que llegue con ella después de completarse el acceso recibe 401 y la API borra la cookie de la sesión recién abierta. Por eso no sale otro código, la vuelta a la contraseña queda inerte hasta la respuesta y, en este paso, la pregunta por la sesión no se repite sola al volver la ventana o la red. Tras entrar tampoco se envía otro código: ya no habría acceso a medias y la pantalla volvería a la contraseña. Si la API no contesta en 30 segundos el paso deja de esperar, como el formulario de la contraseña, y la petición abandonada no se cancela: desde ahí lo anterior ya no se puede garantizar. El acceso a medias vive en el servidor; ni el código ni la contraseña se guardan en el navegador ni van en la URL (en memoria siguen en la caché de escrituras de TanStack Query: se vacía al entrar y, si no se entra, suelta cada envío a los cinco minutos de que el formulario lo deja), y al componente del paso del código no llega la contraseña. Al volver a la contraseña se pregunta otra vez por la sesión, por si una respuesta que se dejó de esperar la abrió.
- **Seguridad de la cuenta (F2-112, ADR-023 §4 y §6):** `/cuenta/seguridad`, fuera de las organizaciones (como `/o`) y con la tarjeta de `/o`; se llega desde las acciones de sesión del menú y de `/o`. Lee `GET /api/v1/auth/mfa/`: con segundo factor dice desde cuándo y cuántos códigos de respaldo quedan (avisa con tres o menos); sin él, ofrece el alta en tres pasos en la misma página (`MfaEnrollment`): la contraseña actual (`POST /auth/mfa/totp/`); la clave en grupos de cuatro, con botón para copiarla y un enlace `otpauth://` que en el móvil abre la aplicación, y el código que esta muestra (`POST /auth/mfa/totp/confirm/`); y los diez códigos de respaldo, una sola vez, para copiarlos o descargarlos como `.txt`, con una casilla «los he guardado» antes de terminar. Errores por `code`: contraseña o código que no valen en su campo; `MFA_ENROLLMENT_NOT_STARTED` vuelve a la contraseña con su aviso; `MFA_ALREADY_ENABLED` enseña el estado; `RATE_LIMITED` dice la espera, en minutos u horas; sin respuesta en 30 segundos deja de esperar. Un código escrito `123 456` se envía junto. `MFA_ALREADY_ENABLED` al confirmar también lleva al estado. Un envío por pulsación; con el alta en curso desaparecen las salidas de la página (volver, acciones de sesión) y el estado no se vuelve a pedir solo, ni al volver la ventana ni la red: cualquiera de esas cosas a mitad de la confirmación perdería los códigos de respaldo o llevaría la cookie anterior a la rotación de la sesión. Las dos peticiones con secretos usan `gcTime: 0`: al terminar no quedan en la caché de escrituras; nada va al almacenamiento ni a la URL. **Límite conocido:** tras los 30 segundos sin respuesta, una confirmación que acabe bien tarde deja el segundo factor activado sin que se vean sus códigos (habrá que regenerarlos); y si se vuelve a pulsar «Activar» mientras aquella sigue en vuelo, la segunda llega con la cookie anterior y la API cierra la sesión. **Código QR (F2-114, [ADR-025](../docs/adr/ADR-025-mfa-enrollment-qr.md)):** el paso de la clave enseña también el QR de la URI `otpauth://` (`QrCode`), dibujado en el navegador: `uqr` 0.1.3 solo calcula la matriz (`encode`, corrección M, margen de 4) y React la pinta como un `<svg>` negro sobre blanco, a 4 px por módulo (unos 230 px; se encoge solo si no cabe en la tarjeta); no se inserta HTML generado y la API no cambia. La clave escrita y el enlace se quedan para quien no puede escanear; el QR tiene un nombre accesible que no lee la clave.
- **Regenerar los códigos y quitar el segundo factor (F2-113, ADR-023 §6 y §8):** con el segundo factor activado, `/cuenta/seguridad` ofrece dos acciones en la misma página (`mfa-manage.tsx`), cada una con la contraseña actual y un código en un solo formulario. «Generar códigos de respaldo nuevos» (`POST /auth/mfa/backup-codes/`) solo admite un código de la aplicación (uno de respaldo se rechaza en su campo y no se gasta) y enseña los diez nuevos una vez, con el mismo paso que el alta (`CodesStep`, sin el aviso de sesiones cerradas: regenerar no las cierra). «Quitar la verificación en dos pasos» (`POST /auth/mfa/disable/`) advierte antes de lo que supone, admite un código de la aplicación o uno de respaldo y, al terminar, el estado dice que ya no está activada y que las demás sesiones se cerraron (lo hace la API). Errores por `code`, como en el alta; `MFA_NOT_ENABLED` (otra pestaña o un envío anterior ya lo quitó; si lo quitó otra sesión, esta ya está cerrada y la API responde 401, que lleva al login) enseña el estado. Tras quitarlo, el foco va al aviso. Mientras una de las dos está en curso desaparecen las salidas de la página y el estado no se vuelve a pedir solo; las dos peticiones usan `gcTime: 0`. **Límite conocido:** quitar el factor rota la sesión; si tras los 30 segundos sin respuesta se vuelve a pulsar «Quitar» y la primera petición acabó bien, la segunda lleva la cookie anterior y la API cierra la sesión (se vuelve a entrar con la contraseña, ya sin segundo factor).
- **Foco y errores:** sin sesión, el foco va al correo. Si falta un campo, el foco va al primero que falta y su aviso se retira al escribir. Un segundo envío mientras el primero está en curso no cuenta. Sin red, el intento falla enseguida con su mensaje; no queda en cola. Si la API no contesta en 30 segundos, el formulario deja de esperar, lo dice y permite reintentar (la petición abandonada no se cancela: si acaba contestando bien, la sesión queda abierta y el siguiente envío entra). Una respuesta que llega justo antes de ese plazo se enseña tal cual, aunque el plazo venza antes de pintarla. Un error de validación de la API (400) muestra el mensaje general, sin marcar el campo: los campos ya limitan su longitud a la del contrato.
- **Rechazos:** el mensaje sale del `code` de la API. `INVALID_CREDENTIALS` no dice si falló el correo o la contraseña. `RATE_LIMITED` muestra la espera de `Retry-After`, en minutos hacia arriba.
- **Destino (`next`):** `safeNext` (`src/lib/next-path.ts`) resuelve el valor como lo haría el navegador y devuelve la ruta ya resuelta, solo si queda en este origen. Se cambian por `/o`: una URL absoluta, `//`, `\`, un carácter de control, una ruta que tras resolver sus puntos empieza por `//` (`/.//otro.sitio`), el propio `/login`, las páginas de recuperación (`/recuperar`, `/restablecer`: un destino con el enlace de otra cuenta en su fragmento dejaría a quien acaba de entrar ante el formulario que cambia la contraseña de esa otra cuenta) y lo que no es una página (`/api/`, `/_next/`). Garantiza que el destino no sale del origen, no que la página exista.
- **`/o`:** organizaciones del usuario (`GET /api/v1/me/organizations/`). Con una sola entra directamente; con varias, lista para elegir; con ninguna, un estado vacío. `/o?elegir` muestra siempre la lista. Cada cambio de estado se anuncia en una región viva, y al reintentar tras un error el foco va al botón nuevo o a la lista que llegó. Con el error en pantalla, volver a la pestaña o recuperar la red no pide nada: lo hace «Reintentar», y así no se pierden el foco ni un aviso del cierre de sesión.
- **Sesión terminada:** `Providers` es el único punto que trata un 401 de una lectura o de una escritura: navega a `/login?next=…` con la ruta en la que estaba. El cierre de sesión trata su propio 401 (`meta.ownSessionEnd`). Es una navegación completa, así que no queda estado en memoria.
- La lista de organizaciones es la que devuelve la API para la sesión. Elegir una no autoriza nada: lo decide la API en cada petición a `/o/[orgSlug]`.

## Recuperar la contraseña: pedir el enlace (F2-90, ADR-021 §2)

- **`/recuperar`:** página pública, fuera de `/o/`: un campo de correo contra `POST /api/v1/auth/password-reset/`. No pide sesión ni la mira, y al abrirse no hace ninguna petición. `/login` enlaza a ella («¿Olvidaste tu contraseña?») y ella de vuelta a `/login`. Componente `PasswordResetRequest`.
- **Un único mensaje:** cuando la API admite la petición (204), el formulario se sustituye por «Revisa tu correo»: el enlace llega si hay una cuenta con ese correo, vale 60 minutos y solo sirve el último. Es el mismo para cualquier correo, porque la API responde lo mismo exista o no la cuenta, y no repite el correo escrito. El foco va a ese título. Desde ahí no se vuelve a enviar: para pedir otro hay que abrir la página de nuevo.
- **Qué es un correo lo decide la API:** la página solo exige que el campo no esté vacío (el aviso se retira al escribir) y envía lo escrito sin espacios exteriores. Si la API no lo acepta (400 en `email`), se dice junto al campo, con el foco en él y sin borrar lo escrito.
- **Errores, por `code`:** `RATE_LIMITED` muestra la espera de `Retry-After`, en minutos hacia arriba; sin red, falla enseguida con su mensaje y no queda en cola; si la API no contesta en 30 segundos, el formulario deja de esperar, lo dice y permite reintentar (la petición abandonada no se cancela: si llegó, el enlace sale igual, y su respuesta tardía no cambia la pantalla); `CSRF_FAILED` pide recargar. Cualquier otro `code` (un 404, un 403 sin permiso, un 400 que no es del correo) se dice como un fallo del servidor: su texto general, como «No encontramos lo que buscas», se leería aquí como «no hay cuenta». Un 401 no es de esta ruta; si llegara, `Providers` llevaría a `/login`, como con cualquier escritura (ver «Acceso»). Ninguno dice nada de ninguna cuenta.
- **Una petición por pulsación:** mientras se envía, el botón queda ocupado (`aria-disabled`, sin perder el foco) y otra pulsación no cuenta. Lo decide el paso que la pantalla enseña, no la llegada de la respuesta.
- **Nada se guarda:** el correo solo viaja en el cuerpo de la petición. No va a la URL (el formulario declara `method="post"`) ni al almacenamiento del navegador.
- **Lo que no hace:** no reenvía desde la pantalla ni cuenta la espera; no avisa de que el servidor de correo no esté configurado (la API tampoco lo dice). La página que cambia la contraseña con el enlace es `/restablecer` (abajo).

## Recuperar la contraseña: cambiarla con el enlace (F2-91, ADR-021 §4 y §5)

- **`/restablecer`:** página pública, fuera de `/o/`, en la ruta exacta que compone la tarea que envía el enlace (`LINK_PATH` en `apps.accounts.recovery`). Un campo de contraseña nueva contra `POST /api/v1/auth/password-reset/confirm/`. No pide sesión ni la mira, y al abrirse no hace ninguna petición. Componente `PasswordResetChange`.
- **El secreto del enlace:** llega en el fragmento de la URL, que el navegador no envía al servidor; el HTML que sirve Next no lo conoce y solo dice «Abriendo el enlace…». Al montar, la página lo lee, lo quita de la barra de direcciones sustituyendo su entrada del historial (`history.replaceState`, con el estado que hubiera) y lo guarda solo en memoria. El router de Next guarda su propia copia de la URL, con el fragmento, y la volvería a escribir en la barra en su siguiente actualización (un `router.refresh()`, por ejemplo): por eso, acabado ese efecto, la página repite el `replaceState` sin estado, que es la forma en que Next se entera de un cambio de URL y lo completa con el suyo. Los tests fijan las dos llamadas; que el secreto no vuelve tras una actualización del router se comprobó en un navegador con la build de producción, no en un test. Next guarda además la primera URL, con su fragmento, en su caché de rutas, y la reutiliza si algo navega a esta misma ruta con el router (`router.replace("/restablecer")` devolvió el secreto a la barra en esa prueba): nada en la aplicación enlaza ni navega a `/restablecer`, y un test lo vigila (`app/restablecer/page.test.tsx` busca la ruta escrita entre comillas en el código de `src`; no ve una ruta compuesta a trozos, y el destino que llega en `next` lo descarta `safeNext`). Viaja solo en el cuerpo de la petición que cambia la contraseña. No llega al DOM, a ninguna URL ni al almacenamiento del navegador, y la caché de escrituras lo suelta, con la contraseña, como mucho un cuarto de segundo después de que la petición termine. Una petición que se deja de esperar (el plazo de 30 segundos, otro enlace en la pestaña, salir de la página) no se cancela: mientras siga sin respuesta, la caché los retiene.
- **Sin enlace** (la página recargada, abierta a mano o recuperada con el botón atrás: el fragmento ya no está en la URL): la página no llama a la API y no dice que el enlace no valga; dice que se abra el enlace del correo, y enlaza a `/recuperar`.
- **Con algo que no tiene la forma de un enlace** (43 caracteres de `[A-Za-z0-9_-]`): tampoco llama a la API; dice que el enlace no vale y enlaza a `/recuperar`.
- **Otro enlace abierto en la misma pestaña** solo cambia el fragmento y la página no se recarga: lo lee igual (`hashchange`), lo quita de la barra y empieza de nuevo con él; lo que quedara en vuelo con el anterior ya no cambia la pantalla.
- **Al cambiarse (204):** el formulario se sustituye por «Contraseña cambiada», con un enlace a `/login` y el foco en ese título. No abre sesión, y dice que las sesiones abiertas se cerraron (lo hace la API).
- **`INVALID_RESET_LINK`:** el enlace no vale. La página lo dice sin decir por qué (la API tampoco lo distingue), deja de ofrecer el formulario, olvida el secreto y enlaza a `/recuperar`.
- **La contraseña la juzga la API:** la página solo exige que no esté vacía y la envía tal cual, sin recortar espacios. Lo que los validadores rechazan (400 en `password`) se dice junto al campo, por el `code` de cada motivo (`password_too_short`, `password_too_common`, `password_entirely_numeric`, `password_too_similar`) y no por el texto de la respuesta; un código sin texto propio usa uno general. El enlace no se gasta y sirve para reintentar. La ayuda del campo y uno de esos textos dicen «12 caracteres»: es el mínimo de `AUTH_PASSWORD_VALIDATORS` del backend, repetido aquí a mano.
- **Otros errores, por `code`:** `RATE_LIMITED` con su espera (o su texto general si no la trae), sin red; cualquier otro, como un fallo del servidor. También `CSRF_FAILED`: su texto general pide recargar, y recargar esta página pierde el enlace (ya no está en la URL: la página pediría abrirlo otra vez desde el correo). Si la API no contesta en 30 segundos el formulario deja de esperar y permite reintentar.
- **Un intento sin respuesta pudo cambiar la contraseña** (el plazo de 30 segundos, o un fallo de red): si después la API dice que el enlace no vale, la página añade que la contraseña puede ser ya la nueva y que se pruebe a entrar con ella, con un enlace a `/login`. Depende solo de lo que pasó en esta página, no de lo que responde la API. Un intento que sí tuvo respuesta no pone la duda ni la quita; la quita abrir otro enlace en la pestaña. Cuenta cualquier fallo de red, también el anterior al envío (sin red, o el token CSRF que no se pudo pedir), en el que la contraseña no llegó a salir: la página no los distingue. Límites, sin test: un 5xx no la pone, tampoco el de un proxy que dejó de esperar; abrir otra vez el mismo enlace también la quita; y vive solo en memoria: recargar la página o abrir el enlace en otra pestaña la pierde.
- **Una petición por pulsación:** como en `/recuperar`, lo decide el paso que la pantalla enseña.
- **Lo que no hace:** no pide la contraseña dos veces ni deja verla; no mide su fortaleza; no abre sesión; sin JavaScript se queda en «Abriendo el enlace…».

## Workspace de una organización (F2-08, ADR-003 §5)

`/o/[orgSlug]` no pinta nada del workspace hasta que la API responde a `GET /api/v1/o/{slug}/me/`, en cada entrada: la respuesta no se guarda entre visitas (`gcTime: 0`). La URL solo selecciona: quién es el usuario ahí y qué puede hacer lo dice la API.

- **Guardia (`TenantGate`):** con la respuesta, monta el shell y deja el contexto en `useTenant()`. Sin sesión (401), `Providers` lleva a `/login` con vuelta a la misma ruta. Organización inexistente o sin membresía (404): la misma página de «no encontrada» que cualquier dirección que no existe. Cualquier otro error al entrar (organización suspendida, red, servidor): una tarjeta con el mensaje de su `code`, reintentar, cambiar de organización y cerrar sesión. Reintentar muestra el aviso de carga y, al terminar, deja el foco en el botón (si vuelve a fallar) o en el workspace (si abre). Con el workspace ya abierto, el contexto se vuelve a pedir al volver a la pestaña o al recuperar la red, si la última respuesta tiene más de 30 segundos: un 401, un 403 o un 404 lo cierran, y sigue cerrado hasta que la API vuelve a responder bien; un fallo pasajero (red, servidor) no cierra el workspace ni lo reabre tras una negativa. Con la tarjeta de error en pantalla, ni volver a la pestaña ni recuperar la red piden nada: lo hace «Reintentar». Si el navegador sabe que no hay red, la petición espera en el aviso de carga y sigue sola al volver la conexión.
- **Navegación por permisos:** `NAVIGATION` (`navigation.ts`) lista las entradas del menú y el permiso del catálogo que da sentido a cada una; `visibleItems` deja las que el usuario puede abrir. Solo se listan módulos que existen: hoy, «Inicio», «Miembros» (`users.view`), «Invitaciones» (`users.invite` y `users.manage`: una entrada puede pedir varios permisos, y entonces hacen falta todos), «Roles» (`roles.view`), «Sucursales» (`organization.view`), «Equipos» (`teams.view`), «Clientes» (`contacts.view`), «Catálogo» (`products.view`), «Inventario» (`inventory.view`), «Precios» (con `anyOf`: basta uno de los cuatro permisos de lectura de precios o `prices.manage`) y «Auditoría» (`audit.view`). Cada fase añade los suyos. Una entrada con `section` también es la actual en las demás páginas bajo esa ruta (`holds`): allí lleva `aria-current="true"` y no `"page"`.
- **Es comodidad, no seguridad:** ocultar una entrada no protege nada. La API comprueba el permiso en cada petición, y una pantalla debe tratar el 403 aunque su entrada estuviera visible.
- **Roles:** se muestran como etiquetas. Nada en la interfaz decide por el nombre o el código de un rol.
- **Cambiar de organización:** enlace a `/o?elegir`.
- **Cerrar sesión:** `POST /api/v1/auth/logout/`; al responder se vacía la caché de datos y se va a `/login`. Un 401 al cerrar significa que la sesión ya no existía y se trata igual. Otro error se muestra encima de las acciones y la sesión sigue abierta; sin red el cierre falla enseguida y no queda en cola. Desde que se pulsa hasta que la página cambia el botón queda ocupado (`aria-disabled`, sin perder el foco) y una segunda pulsación no cuenta. Está en la barra lateral, en la tarjeta de error de la guardia y en `/o` (con la lista, con «sin organizaciones» y con el error; ahí sin «Cambiar de organización»). Es el mismo componente, `SessionActions`.
- **Título de la pestaña:** «Workspace · Good Doggy CRM» hasta que la API responde; después, el nombre de la organización, precedido por la sección si no es el inicio.
- **Inicio:** saluda con el nombre que da la API, muestra la organización y los roles. No hay datos de ejemplo: los módulos de negocio llegan con sus fases.

## Miembros (F2-17)

`/o/[orgSlug]/miembros` muestra quién pertenece a la organización, con su estado, sus roles y su sucursal: lo que devuelve `GET /api/v1/o/{slug}/members/` (F2-16), con el cliente generado.

- **Componente:** `components/members/members-list.tsx`, sobre la lista por cursor compartida (abajo). Por miembro: nombre (o el correo si no tiene), correo, roles como etiquetas, sucursal, estado de la membresía y fecha de alta en la zona horaria de la aplicación. Un nombre o un correo largo se parte en varias líneas; no se recorta.
- **Paginación:** por cursor (ADR-016). «Cargar más» pide la página siguiente con el `next` de la anterior y desaparece cuando la API devuelve `null`. Desde la pulsación hasta la respuesta el botón queda ocupado (`aria-disabled`), también si el navegador sabe que no hay red y la petición espera. Al llegar la página el foco pasa a su primera fila, salvo que ya se haya ido a otra parte. Si esa página falla, lo ya cargado sigue en pantalla (salvo con un 403, que cierra la lista), el aviso aparece al lado del botón (no lo mueve) y el mismo botón reintenta; al reintentar el aviso se quita y vuelve si falla otra vez.
- **Estados:** cargando; error con «Reintentar» (el botón no se desmonta mientras reintenta, y al abrir la lista el foco va al título); y sin permiso (403), con un mensaje propio y sin reintento.
- **Negativas y sesión:** un 403 cierra la lista aunque ya estuviera en pantalla, y sigue cerrada hasta que la API vuelve a responder bien (un fallo pasajero no la reabre); si llega al reintentar o al cargar más, el foco va al título, salvo que el usuario ya lo haya llevado a otra parte. Sin sesión (401) no se muestra un error, tampoco al cargar más: `Providers` lleva al login. La lista no se guarda entre visitas (`gcTime: 0`): cada entrada pregunta a la API.
- **Navegación:** la entrada «Miembros» pide el permiso `users.view`. Es comodidad: quien abre la URL sin el permiso ve el mensaje de «sin permiso» porque la API responde 403.
- **Roles y estado:** se muestran tal como llegan. Nada decide por el nombre o el código de un rol. El estado es el de la membresía, no el de la cuenta.
- **Sucursal (F2-71):** bajo los roles, «Sucursal: nombre (código)» con el `default_branch` de la fila (F2-70), o «Sin sucursal» si es `null`. Llega con el directorio: no hay otra petición ni otro permiso, y la ve quien ve la lista. La pantalla no dice si esa sucursal está inactiva, porque el directorio no lo trae. Se cambia con «Sucursal» (ver «Asignar la sucursal»).
- **Título de la pestaña:** «Miembros · organización · Good Doggy CRM». Lo pone el shell a partir de la entrada de navegación de la ruta.
- Invitar y dar de baja son otros work items.

### Lista por cursor compartida (F2-24)

`components/lists/cursor-list.tsx` (`CursorList`) tiene lo que una pantalla de gestión necesita para listar por cursor: título, lista, «Cargar más» y los estados de carga, error con reintento, sin permiso (403) y sin sesión (401), con el comportamiento y el foco descritos arriba. La pantalla aporta la clave de la consulta, la función que pide una página, el contenido de cada fila y sus textos (`section`: el espacio de mensajes con `eyebrow`, `title`, `intro`, `loading`, `denied`, `count`, `more` y `loadingMore`). También recibe el nombre de la organización (para `intro`, que lleva `{organization}`; `count` lleva `{count}`) y, si quiere, clases para la fila (`rowClassName`). Una sección a la que le falte alguno de esos textos no compila. `controls` son los controles de la pantalla (filtros), entre el título y la lista: no se desmontan cuando la lista se vuelve a pedir, falla, cambia de clave o se cierra con un 403, así que conservan el foco (F2-76); `notice` es un aviso de la pantalla encima de la lista, que solo se pinta con la lista ya cargada; `empty`, lo que la pantalla quiere enseñar en lugar de una lista sin filas (sin él se pinta la lista vacía; el aviso, el recuento y «Cargar más» no cambian); el `ref` le permite volver a pedir la lista y llevar el foco al título mientras la pantalla está montada; `keep`, las filas que la pantalla sostiene aunque la lista nueva ya no las traiga (un formulario abierto en una fila que se borró en otra pestaña): siguen en el sitio que tenían, para no perder lo escrito ni el foco, y no cuentan en `count` ni en las filas que recibe `children`. La usan las pantallas de miembros, de invitaciones, de roles, de sucursales, de equipos y de auditoría; las siguientes listas de gestión se construyen sobre ella.

### Suspender y reactivar (F2-21)

Cada fila ofrece «Suspender» (miembro activo) o «Reactivar» (miembro suspendido), con `PUT /api/v1/o/{slug}/members/{id}/status/` (F2-19). Componente: `components/members/member-status-action.tsx`.

- **A quién se ofrece:** a quien tiene el permiso `users.manage` según el contexto de la API. Nunca en la fila propia ni en miembros invitados o dados de baja. Es comodidad: las reglas las aplica la API (ADR-017) y un 403 se explica en la fila.
- **Confirmación:** en la propia fila, con la consecuencia («perderá el acceso… y se cerrarán sus sesiones»), asociada al grupo (`aria-describedby`). Nada se envía sin confirmar. Al abrirla el foco va a «Cancelar».
- **Lo que se confirma queda fijado al abrir.** Si la lista cambia debajo (otra persona suspendió al miembro), la pregunta y lo que se envía no se dan la vuelta. Si el miembro ya está en el estado pedido y nada se está enviando, la confirmación se cierra y se anuncia ese estado.
- **Un envío:** una marca síncrona impide que dos pulsaciones seguidas sean dos peticiones, y se suelta cuando la pantalla ya enseña el resultado, no al llegar la respuesta (F2-28); el botón queda ocupado (`aria-disabled`) hasta entonces. Sin red falla y se dice: una escritura no queda en cola.
- **Éxito:** se cancela cualquier lectura de la lista que estuviera en vuelo (traería el estado anterior a la escritura) y la fila cambia en la lista ya cargada, con el estado que respondió la API. No se vuelven a pedir sus páginas, salvo que lo cancelado fuera una lectura de la lista entera: esa se repite después. Un «Cargar más» cancelado así vuelve a quedar libre: hay que pulsarlo otra vez. El resultado se anuncia (`role="status"`) y el foco pasa a la acción nueva si el usuario no se ha ido a otra parte.
- **Errores que conservan la acción** (`PERMISSION_DENIED`, con un texto propio; `LAST_OWNER`; red; fallo del servidor): se explican en la fila, por código, y el mismo botón reintenta.
- **Pantalla desfasada** (`INVALID_TRANSITION`, `NOT_FOUND`): la lista se vuelve a pedir, y la acción, o la fila entera, puede desaparecer. Por eso el aviso («El estado de … ya había cambiado») vive en la lista (`role="alert"`), no en la fila, y el foco va al título si seguía en esa acción (o en ninguna parte). Si la nueva lectura falla, el aviso se queda y la lista no cambia. El aviso se quita al abrir otra confirmación.
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.

### Asignar y quitar roles (F2-27)

Cada fila ofrece «Roles», que abre un panel con los roles de la organización: «Asignar» los que el miembro no tiene y «Quitar» los que tiene, con `PUT` y `DELETE /api/v1/o/{slug}/members/{id}/roles/{role_id}/` (F2-25). Componente: `components/members/member-roles-action.tsx`.

- **A quién se ofrece:** a quien tiene `users.manage` y `roles.view` según el contexto de la API (el panel necesita ver los roles). Nunca en la fila propia; el estado del miembro no importa. Es comodidad: las reglas contra la escalada las aplica la API (ADR-003 §5) y un 403 se explica en el panel.
- **Dos pasos:** abrir el panel y pulsar el botón del rol. Abrir no envía nada. Conceder un rol no pide otra confirmación, tampoco el de Owner: nada en la pantalla decide por el nombre o el código de un rol, y las reglas las aplica la API. Al abrir, el foco va a «Cerrar».
- **Roles del panel:** los de la organización, todas sus páginas, pedidos al abrir y vueltos a pedir en cada apertura. No se vuelven a pedir solos (al volver a la pestaña o al recuperar la red). Si la petición falla, «Reintentar» no se desmonta mientras reintenta y, al llegar los roles, el foco pasa a «Cerrar» si seguía en ese botón o en ninguna parte. Al reabrir, la lista anterior sigue en pantalla mientras llega la nueva. Un cursor que no avanza se trata como un error, no como una lista sin fin.
- **Lo que hace cada botón queda fijado al abrir.** Los roles que el miembro tiene se anotan al abrir el panel y solo cambian con las respuestas propias: si la lista cambia debajo, ningún botón pasa de «Asignar» a «Quitar» por sí solo.
- **Un cambio cada vez**, enviado una sola vez. La marca que lo impide se suelta cuando la pantalla ya enseña el resultado, no al llegar la respuesta. Mientras tanto todos los botones del panel quedan ocupados (`aria-disabled`) y solo el pulsado lo dice (`aria-busy`). Sin red falla y se dice.
- **Una pulsación de más no deshace:** al terminar, el botón pulsado pasa a la acción contraria y conserva el foco; el segundo clic de un doble clic y un Enter mantenido se ignoran.
- **Éxito:** como al suspender, se cancela la lectura de la lista que estuviera en vuelo y los roles de la fila cambian en la lista ya cargada, por nombre y, a igualdad, por código. Ese orden es una aproximación al del directorio (la intercalación de la base); la siguiente lectura trae el exacto. El resultado se anuncia (`role="status"`).
- **Errores que conservan el panel** (`PERMISSION_DENIED`, con un texto propio; `LAST_OWNER`; red; fallo del servidor): se explican en el panel y el mismo botón reintenta.
- **Pantalla desfasada** (404: el miembro o el rol ya no existen, o ya no tiene ese rol): el panel se cierra, la lista y los roles se vuelven a pedir y lo explica el aviso de la lista, con su propio texto («Los roles de … ya habían cambiado»).
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.

### Asignar la sucursal (F2-72)

Cada tarjeta ofrece «Sucursal», que abre un panel con un selector: «Sin sucursal» y las sucursales de la organización (`GET /api/v1/o/{slug}/branches/`, todas las páginas, pedidas al abrir y de nuevo en cada apertura), con la del miembro elegida. «Guardar» envía `PUT /api/v1/o/{slug}/members/{id}/branch/` con `{"branch_id": "<id>"}` o `{"branch_id": null}` (F2-69). Componente: `components/members/member-branch-action.tsx`, hermano del panel «Roles»: mismas reglas de envío, foco y errores.

- **A quién se ofrece:** a quien tiene `users.manage` y `organization.view` (el selector lee las sucursales) según el contexto de la API. Nunca en la fila propia; el estado de la membresía no importa. Es comodidad: las reglas las aplica la API (ADR-017: cubrir los roles del miembro) y un 403 se explica en el panel.
- **A quién:** el nombre accesible del botón y el título del panel llevan el nombre y el correo, porque dos personas pueden llamarse igual.
- **Selector:** cada sucursal como «nombre (código)»; una inactiva lo dice y se puede elegir, porque la API la admite. Lo elegido parte de la sucursal que el miembro tenía al abrir y no cambia si la lista cambia debajo; esa sucursal figura siempre entre las opciones. Al reabrir, también en otra tarjeta, las opciones anteriores siguen en pantalla mientras llegan las nuevas. Sin sucursales en la organización, el panel lo dice.
- **Envío:** una petición por pulsación; «Guardar» sin haber cambiado nada respecto a la sucursal que el miembro tenía al abrir cierra el panel y no envía, aunque la tarjeta haya cambiado debajo (para pisar ese cambio hay que reabrir); mientras se envía, lo elegido no cambia y «Cancelar» no cierra; una tecla mantenida no cuenta; sin red, falla y se dice.
- **Éxito:** la tarjeta enseña la sucursal que respondió la API, sin volver a pedir la lista; el panel se cierra, el foco vuelve a «Sucursal» y se anuncia. Una lectura de la lista en vuelo se cancela para que no pise la fila, y se repite si era la lista entera.
- **Errores, por `code`, en el panel:** sin permiso (con un texto propio), `LAST_OWNER`, red o fallo del servidor; «Guardar» reintenta. Un 400 se explica como fallo del servidor: las opciones salen de la API y las sucursales no se borran. Sin sesión (401), `Providers` lleva al login. Un 404 es pantalla desfasada: el panel se cierra, la lista se vuelve a pedir y lo explica el aviso de la lista. Si falla la lectura de las sucursales, se explica con «Reintentar».
- **Foco:** al abrir, a «Cancelar», que no cambia nada; al cerrar, a «Sucursal», salvo con un 404: entonces va al título de la lista, si seguía en la acción o en ninguna parte.

## Invitaciones (F2-83 a F2-85)

`/o/[orgSlug]/invitaciones` muestra las invitaciones de la organización: lo que devuelve `GET /api/v1/o/{slug}/invitations/` (F2-81), de la más reciente a la más antigua, con el cliente generado. Componente: `components/invitations/invitations-list.tsx`, sobre la lista compartida. Encima de la lista está «Invitar» (F2-84) y cada fila pendiente o caducada ofrece «Revocar» (F2-85), los dos abajo. Todavía ninguna invitación se envía ni se puede aceptar (D-F2-14).

- **Cada fila:** el correo invitado y cuándo se invitó; sus roles; su estado («Pendiente», «Caducada», «Revocada», «Aceptada») y, si está pendiente o caducada, su fecha de caducidad. Las fechas, en la zona de la aplicación. El estado es el que la API enseña: una pendiente cuya fecha pasó ya llega como caducada; la pantalla no lo recalcula mientras sigue abierta.
- **Roles por su nombre:** la invitación solo trae identificadores. A quien tiene `roles.view` según el contexto de la API se le pide el directorio de roles entero (`lib/all-pages.ts`) y se empareja aquí, en el orden de la invitación; un identificador que ya no está en el directorio se enseña como «Un rol que ya no existe». A quien no lo tiene no se le pide, y la fila dice cuántos roles son. Si el directorio falla o tarda, la lista funciona igual, con el recuento: no es su error.
- **Ningún identificador llega a la pantalla:** ni el de la invitación, ni los de sus roles, ni el de quien invitó (que no se enseña todavía).
- **Un estado que esta versión no conoce** se enseña con su código.
- **Sin invitaciones:** la pantalla lo dice en lugar de enseñar una lista vacía.
- **Navegación:** la entrada «Invitaciones», después de «Miembros», se ofrece a quien tiene `users.invite` y `users.manage`, los dos que pide la API. Es comodidad: quien entre por la URL sin ellos ve el 403 explicado.
- El directorio de roles se guarda con su propia clave de consulta y no queda en memoria al salir.

### Invitar (F2-84)

«Invitar» abre un formulario encima de la lista: el correo de la persona y los roles que tendrá al aceptar, con `POST /api/v1/o/{slug}/invitations/` (F2-80). Componente: `components/invitations/invitation-create.tsx`, sobre `FieldsForm`.

- **A quién se ofrece:** a quien tiene `users.invite`, `users.manage` y `roles.view` según el contexto de la API. Sin ver los roles no hay entre qué elegir. Es comodidad: qué roles puede dar cada quien lo decide la API.
- **Los roles** son casillas con el nombre de cada rol del directorio que ya lee la lista, en su orden. Se ofrecen todos; la API responde 403 si quien invita no podría asignar alguno. Las casillas no llevan valor: ningún identificador de rol llega a la pantalla. Mientras el directorio no llega, o si falló sin haber llegado, el formulario lo dice y no hay casillas; un fallo posterior deja las que ya había. Cada apertura del formulario vuelve a pedir el directorio: por eso sirve cerrarlo y abrirlo, que es lo que piden el aviso de que no llegó y el de un rol que ya no existe.
- **Antes de enviar:** el correo es obligatorio, y hay que elegir entre 1 y 20 roles; si no, no se envía nada y se dice junto al correo o junto a los roles, con el foco allí.
- **Lo que se envía:** el correo sin espacios exteriores (su forma la decide la API) y los identificadores de los roles, en el orden en que se eligieron. Un rol que desaparece del directorio con el formulario abierto deja de verse, y entonces ni cuenta ni se envía. Una petición por pulsación.
- **Errores, por `code`:** junto al correo, que no sirve (400 en `email`), que ya es miembro (`ALREADY_MEMBER`) o que ya tiene una invitación, pendiente o caducada (`INVITATION_PENDING`). En el formulario: un rol elegido ya no existe (400 en `role_ids`), sin permiso para invitar con esos roles (403), 50 pendientes o caducadas (`INVITATION_LIMIT`), 100 en 24 horas (`RATE_LIMITED`, con su propio texto y no el del acceso) y los demás. Cambiar el correo o lo elegido retira el error anterior.
- **No da a entender que se envió un correo:** el formulario y el anuncio dicen que la invitación queda registrada y que el correo todavía no se envía.
- **Al crearla:** el formulario se cierra, el anuncio lleva el correo tal como lo guardó la API, el foco vuelve a «Invitar» y la lista se vuelve a pedir (la invitación nueva va al principio).

### Revocar (F2-85)

Cada fila pendiente o caducada ofrece «Revocar», que pide confirmación en la propia fila y envía `PUT /api/v1/o/{slug}/invitations/{id}/status/` con `{"status": "REVOKED"}` (F2-82). Componente: `components/invitations/invitation-revoke-action.tsx`, hermana de «Desactivar» en sucursales.

- **A quién se ofrece:** a quien tiene `users.invite` y `users.manage` según el contexto de la API, en las filas que la lista enseña como «Pendiente» o «Caducada». Es comodidad: si esa persona puede revocar esa invitación (cubre sus roles) lo decide la API.
- **La confirmación** dice la consecuencia (deja de poder aceptarse, el correo se puede invitar otra vez, no se deshace) y abre con el foco en «Cancelar». El nombre accesible del botón lleva el correo.
- **Al revocar:** una petición por pulsación. La fila pasa al estado que respondió la API sin volver a pedir la lista, y deja de ofrecer la acción. Como sus controles desaparecen, el resultado lo anuncia la lista (una región `status` siempre montada, encima) y el foco va al título si seguía en la fila.
- **Errores, por `code`:** sin permiso para esa invitación (403), en la confirmación, que sigue abierta. Si ya no estaba pendiente (409 `INVALID_TRANSITION`) o ya no está al alcance (404), la confirmación se cierra, la lista se vuelve a pedir y lo explica un aviso de la lista. Abrir otra confirmación o «Invitar», o registrar una invitación con el formulario ya abierto, retira el aviso y el anuncio.
- **Si la fila deja de estar pendiente con la confirmación abierta** (otra persona la revocó y la lista se volvió a pedir), la confirmación desaparece sin error y el foco va al título.
- **Lecturas en vuelo:** como en sucursales, una lectura que salió antes de la escritura se cancela para que no devuelva la fila a «Pendiente», y si era la lista entera se repite.

## Roles (F2-23)

`/o/[orgSlug]/roles` muestra los roles de la organización: lo que devuelve `GET /api/v1/o/{slug}/roles/` (F2-22), con el cliente generado.

- **Componente:** `components/roles/roles-list.tsx`, sobre la lista por cursor compartida (ver «Miembros»): su paginación, sus estados y su foco son los mismos.
- **Por rol:** nombre, si es de plantilla o propio, descripción si la tiene, número de miembros y sus permisos, cada uno con su alcance si lo admite.
- **Nombres de los permisos:** salen de `catalog.*` en `messages/es-PE.json` (`catalog.users.manage` para `users.manage`); los alcances, de `roles.scope.*`. Son textos planos, sin formato ICU. Un permiso o un alcance que esos textos no conocen se enseña con su código: no se oculta. El código llega de la API, así que el texto se busca por propiedades propias y no como una ruta de mensajes.
- **Navegación:** la entrada «Roles» pide el permiso `roles.view`; `users.view` no basta. Es comodidad: quien abre la URL sin el permiso ve «sin permiso» porque la API responde 403.
- **Lo que se ve es lectura.** Nada decide por el nombre o el código de un rol. Crear un rol está en «Crear un rol»; renombrarlo, en «Editar un rol»; conceder y retirar sus permisos, en «Permisos de un rol»; borrarlo, en «Borrar un rol».

### Crear un rol (F2-35)

Encima de la lista, «Crear rol» abre un formulario con nombre y descripción y envía `POST /api/v1/o/{slug}/roles/` (F2-29). Componente: `components/roles/role-create.tsx`. El rol nace sin permisos.

- **A quién se ofrece:** a quien tiene `roles.manage` según el contexto de la API y además ve la lista (`roles.view`): el formulario vive sobre ella. Es comodidad: la API decide, y un 403 se explica en el formulario.
- **Abrir no envía nada.** El foco va al nombre. «Cancelar» cierra, descarta lo escrito y devuelve el foco a «Crear rol».
- **Un envío:** la misma marca síncrona de las demás escrituras; Enter, un segundo clic, «Cancelar» o seguir escribiendo mientras se envía no hacen nada, y un Enter mantenido no repite la pulsación. Sin red falla y se dice.
- **Lo que valida la pantalla:** que haya nombre, y las longitudes máximas de los campos. Lo demás lo decide la API: se envía lo escrito sin sus espacios exteriores y se anuncia el nombre que la API guardó.
- **Éxito:** el formulario se cierra, el resultado se anuncia (`role="status"`, visible) y la lista en pantalla se vuelve a pedir. El rol nuevo va al final: si hay «Cargar más», aparece al cargar la última página. Un «Cargar más» que estuviera en vuelo se cancela y hay que pulsarlo otra vez. Si esa relectura falla, el aviso se queda y la lista no cambia; si la API niega la lista (403), la pantalla se cierra con su aviso de «sin permiso». El foco vuelve a «Crear rol».
- **Errores, por `code`:** los del nombre (`ROLE_NAME_TAKEN`, o un 400 con el campo `name`) y los de la descripción se explican junto a su campo; un error del nombre lleva el foco al nombre. Sin permiso, `LAST_OWNER`, red o fallo del servidor, en el formulario. Lo escrito no se pierde, y al escribir en cualquier campo los errores se retiran hasta el siguiente envío. Nunca se enseña el texto de la respuesta.
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.

### Editar un rol (F2-39)

Cada rol editable ofrece «Editar», que abre un formulario con su nombre y su descripción y envía `PATCH /api/v1/o/{slug}/roles/{id}/` (F2-38). Componente: `components/roles/role-edit-action.tsx`, hermano de «Crear rol»: los mismos campos y textos, y las mismas reglas de envío, foco y errores.

- **A quién se ofrece:** a quien tiene `roles.manage` según el contexto de la API, y solo en los roles que la API marca `editable`. Una plantilla que no sea el Owner se puede renombrar: lo decide `editable`, no `is_system`. Es comodidad: la API exige además cubrir todos los permisos del rol, y un 403 se explica en el formulario.
- **Lo que se edita queda fijado al abrir**: si la lista cambia debajo, el formulario sigue con lo que el usuario abrió. «Cancelar» descarta lo escrito.
- **Un envío:** Enter, un segundo clic, «Cancelar» o seguir escribiendo mientras se envía no hacen nada, y un Enter mantenido no repite la pulsación. Se envían siempre los dos campos, sin sus espacios exteriores; la API no escribe lo que no cambia.
- **Éxito:** se cancela la lectura de la lista que estuviera en vuelo y la tarjeta enseña el nombre y la descripción que guardó la API, sin volver a pedir las páginas; lo demás de la fila no se toca (la respuesta puede ser anterior a un cambio de «Permisos» hecho mientras tanto). Si lo cancelado era la lista entera, se repite después; un «Cargar más» cancelado hay que pulsarlo otra vez. El resultado se anuncia (`role="status"`, no visible) y el foco vuelve a «Editar», salvo que el usuario ya esté en otra parte. Si la API responde con otro rol, no se da por guardado: se explica como un fallo nuestro y la lista se vuelve a pedir.
- **Errores, por `code`:** los del nombre (`ROLE_NAME_TAKEN`, o un 400 con el campo `name`) y los de la descripción, junto a su campo; `PERMISSION_DENIED` (con un texto propio: hace falta cubrir los permisos del rol y, si alguno es sensible, ser Owner, y el rol no puede ser uno que quien mira tenga asignado; la API no dice cuál de las reglas fue), `LAST_OWNER`, red o fallo del servidor, en el formulario. Lo escrito no se pierde, y al escribir en cualquier campo los errores se retiran hasta el siguiente envío.
- **Pantalla desfasada (404):** el rol ya no existe. El formulario se cierra, la lista se vuelve a pedir y lo explica un aviso de la lista; el foco va al título si seguía en la tarjeta del rol (el formulario o su panel «Permisos») o en ninguna parte.
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.
- **Límites conocidos:** se envían los dos campos con lo fijado al abrir: el que no se toca pisa lo que otra persona hubiera cambiado en él mientras tanto. Si una relectura de la lista trae el rol como no editable con el formulario abierto, el formulario se desmonta sin aviso: lo escrito se pierde, el foco se queda sin destino y un envío que estuviera en vuelo cambia la tarjeta pero no se anuncia.

### Borrar un rol (F2-40)

Cada rol editable que no es de plantilla ofrece «Borrar», con `DELETE /api/v1/o/{slug}/roles/{id}/` (F2-38). Componente: `components/roles/role-delete-action.tsx`. No se puede deshacer: pide confirmación en la tarjeta, como «Suspender» en la pantalla de miembros.

- **A quién se ofrece:** a quien tiene `roles.manage` según el contexto de la API, en los roles que la API marca `editable` y que no son de plantilla (`is_system`: la API no borra una plantilla). Un rol con miembros también la ofrece: la API responde que no y la tarjeta lo explica. Es comodidad: la API exige además cubrir todos los permisos del rol.
- **Confirmación:** en la propia tarjeta, con la consecuencia, asociada al grupo (`aria-describedby`). Nada se envía sin confirmar. Al abrirla el foco va a «Cancelar». El rol que se nombra queda fijado al abrir.
- **Un envío:** la misma marca síncrona de las demás escrituras; tras el éxito la confirmación sigue ocupada hasta que la tarjeta desaparece. Sin red falla y se dice.
- **Éxito:** se cancela la lectura de la lista que estuviera en vuelo y la tarjeta se quita de la lista ya cargada. Como la tarjeta ya no está, el resultado lo anuncia la lista (`role="status"`, visible) y el foco va al título si seguía en la tarjeta o en ninguna parte. El anuncio se quita al abrir otra acción de la lista, también «Crear rol».
- **Errores, por `code`, en la tarjeta:** `PERMISSION_DENIED` (con un texto propio), `ROLE_IN_USE`, `ROLE_IS_SYSTEM`, `LAST_OWNER`, red o fallo del servidor. El mismo botón reintenta. Con `ROLE_IN_USE` la lista se vuelve a pedir además: la tarjeta podía decir «Sin miembros».
- **Pantalla desfasada (404):** el rol ya no existía. La confirmación se cierra, la lista se vuelve a pedir y lo explica un aviso de la lista (`role="alert"`).
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.
- **Límites conocidos:** un «Cargar más» cancelado al borrar hay que pulsarlo otra vez; una lectura de la lista entera cancelada se repite después. Si una relectura trae el rol como no editable con la confirmación abierta, la confirmación se desmonta sin aviso y el foco se queda sin destino; de un envío que estuviera en vuelo, el borrado se anuncia igual en la lista, pero un error que no sea el 404 no se enseña. De dos resultados seguidos (un borrado y un aviso de pantalla desfasada) solo se ve el último. El aviso de «Crear un rol» no se quita al borrar ese rol: los dos textos quedan a la vista.

### Permisos de un rol (F2-36)

Cada rol editable ofrece «Permisos», que abre un panel con el catálogo (`GET /api/v1/o/{slug}/permissions/`, F2-34): «Conceder» los que el rol no tiene y «Retirar» los que tiene, con `PUT` y `DELETE /api/v1/o/{slug}/roles/{id}/permissions/{code}/` (F2-31, F2-33). Componente: `components/roles/role-permissions-action.tsx`, hermano del panel «Roles» de la pantalla de miembros: mismas reglas de envío, foco y errores.

- **A quién se ofrece:** a quien tiene `roles.manage` según el contexto de la API, y solo en los roles que la API marca `editable`: no el rol Owner ni uno que tenga asignado quien mira (no confundir con la etiqueta «Propio» de la tarjeta, que es un rol que no es de plantilla: esos sí se editan). Lo decide `editable`, no `is_system`. Es comodidad: las reglas contra la escalada las aplica la API (ADR-003 §5), y un 403 se explica en el panel.
- **A quién alcanza:** el panel dice cuántos miembros tiene el rol. Lo que se cambia les llega a todos en su siguiente petición.
- **Catálogo:** se pide al abrir y en cada apertura; al reabrir se enseña el de la vez anterior hasta que llega el nuevo. Los nombres salen de `catalog.*` en los textos; un permiso sin texto se enseña con su código. Los sensibles llevan la marca «Sensible».
- **El código va codificado en la ruta** (F2-37): el cliente generado lo pone tal cual, y es texto que llega de la API. Un código hecho solo de puntos no se envía y se explica como un fallo nuestro.
- **Permisos con alcance:** se enseñan con su alcance, o como «Sin conceder», sin botón. Elegir el alcance llegará con el primer permiso del catálogo que lo use.
- **Lo que hace cada botón queda fijado al abrir**, y solo cambia con las respuestas propias. Un cambio cada vez, enviado una sola vez; el segundo clic de un doble clic y un Enter mantenido se ignoran.
- **Éxito:** se cancela la lectura de la lista que estuviera en vuelo y los permisos de la tarjeta cambian en la lista ya cargada. El resultado se anuncia y el botón, ya con la acción contraria, conserva el foco.
- **Errores, por `code`:** `PERMISSION_DENIED` (con un texto propio: hace falta tener el permiso y, si es sensible, ser Owner, y el rol no puede ser uno que quien mira tenga asignado; la API no dice cuál de las reglas fue), `LAST_OWNER`, red o fallo del servidor se explican en el panel y el mismo botón reintenta.
- **Pantalla desfasada (404):** el rol ya no existe o ya no tiene esa concesión. El panel se cierra, la lista se vuelve a pedir y lo explica un aviso de la lista (`role="alert"`); el foco va al título si seguía en el panel.
- **Sin sesión (401):** no se muestra un error; `Providers` lleva al login con vuelta a la pantalla.
- **Límite conocido:** si una relectura de la lista trae el rol como no editable con su panel abierto, el panel se desmonta sin aviso: el foco se queda sin destino y un cambio que estuviera en vuelo cambia la tarjeta pero no se anuncia.

### Formulario de campos compartido (F2-48)

`components/forms/fields-form.tsx` (`FieldsForm`) tiene el camino de envío de un formulario de campos de texto, el que describen «Crear un rol» y «Crear una sucursal». Hoy lo usan «Crear sucursal», «Editar sucursal», «Crear equipo», «Editar equipo», «Invitar» y «Crear cliente»; los formularios de roles conservan su copia.

- **Lo que hace:** pinta los campos, «Cancelar» y el botón de envío; comprueba los obligatorios; envía una vez por pulsación; explica los errores de la API por `code` (los de un campo, junto a él; los demás, en el formulario; un 401, ocupado y sin error); y mueve el foco al primer campo al abrir y al primer campo con error si el foco seguía en el botón o en ninguna parte.
- **Lo que pone la pantalla:** la escritura (el resultado de `useMutation`), qué hacer con lo escrito (`send`, que recibe los valores sin espacios exteriores), los campos con sus textos ya resueltos (etiqueta, límite, ayuda, aviso de obligatorio y de no válido) y, si hace falta, su valor inicial y el `id` de una lista de sugerencias, el error propio de esta escritura (`taken`: un código repetido, junto a su campo; si no nombra campo, es del formulario entero y sustituye al genérico), una comprobación propia antes de enviar (`check`: algo que la pantalla pide además de los campos de texto, como elegir un rol; si no se cumple no se envía, se retira el error anterior y la pantalla lo dice junto a su control), y el texto de «sin permiso». Lo que la pantalla ponga en `note` está dentro del formulario: cambiar una casilla o un campo suyo (lo que emite `input`) retira el error anterior, como escribir en un campo del formulario. Abrir y cerrar, el botón que abre, el anuncio del resultado, lo que pasa con la lista y la guarda del Enter mantenido siguen en la pantalla.
- **La marca de envío vive en el formulario** y se suelta en un efecto de maquetación cuando la escritura ya no está en curso. Un render solo del formulario (por ejemplo, al retirar un aviso de «falta» justo antes de enviar) trae la escritura tal como era antes de enviar y no la suelta: se compara con la que había al enviar. Por eso `write` debe ser el resultado de `useMutation` del render de la pantalla, no un objeto guardado, y `send` debe iniciar esa escritura antes de volver (`mutate`, sin esperar a nada): si no la inicia, el formulario deja de responder —también «Cancelar»— hasta el siguiente render de la pantalla; si la inicia más tarde, un render de la pantalla entre medias suelta la marca y otra pulsación sería otra escritura.
- **El formulario se monta al abrir y se desmonta al cerrar:** los avisos y lo escrito no sobreviven a un cierre.

Abrir «Editar», «Desactivar» o «Reactivar» (F2-63), «Integrantes» (F2-64) o «Crear equipo» retira ese aviso; cancelar otro formulario, no.

### Integrantes de un equipo (F2-64)

El nombre accesible lleva el nombre y el identificador del equipo.

Componente: `components/teams/team-member-add.tsx`.

- **Candidatos:** todos los miembros de la organización (`GET …/members/`, todas las páginas, pedidas al abrir la lista y de nuevo en cada apertura), menos quien ya está en el equipo, quien tiene la membresía dada de baja y uno mismo. La API no deja que nadie se incorpore a sí mismo, y la lista lo dice a quien no está en el equipo. Sin búsqueda ni filtro. Cada candidato se enseña con su nombre y su correo (solo el correo si no tiene nombre), y el nombre accesible de «Incorporar» lleva los dos: dos personas pueden llamarse igual.
- **Entra con lo que pone la API** (integrante, activo): no se elige el papel. El panel enseña el papel que respondió la API.

La lista sigue abierta para incorporar a más, y el foco pasa a «Listo».

Si lo que falla es la lectura de los miembros, se explica con «Reintentar»; al pulsarlo el foco pasa a «Listo», porque el botón desaparece mientras se vuelve a pedir.

- **Si se cierra el panel con una incorporación en vuelo**, la escritura sigue su curso en la API. Si sale bien no se anuncia y el panel reabierto la enseña: si su lectura seguía en vuelo al llegar la respuesta, se cancela y se vuelve a pedir. Si falla, solo un 404 avisa (en la lista, como siempre); cualquier otro fallo no se dice, y el panel reabierto enseña que la persona no entró.

### Cambiar el papel de un integrante (F2-67)

En el panel de integrantes, cada fila ofrece «Hacer supervisor» o «Hacer integrante», lo contrario de su papel, que envía `PUT /api/v1/o/{slug}/teams/{team_id}/members/{membership_id}/` con `team_role` (F2-58). Componente: `components/teams/team-member-role.tsx`.

A quien tiene un papel que esta versión no conoce no se le ofrece cambio. Es comodidad: la API decide, y un 403 se explica en la fila.

- **A quién:** el nombre accesible lleva el nombre y el correo.
- **Éxito:** la fila enseña al integrante como lo respondió la API (su papel, y también su estado), sin volver a pedir los integrantes. El botón pasa a la acción contraria en el mismo render que deja pulsar otra vez. El resultado se anuncia en la fila (`role="status"`), con el papel que respondió la API, no el que se pidió.

## Auditoría (F2-75 a F2-77)

`/o/[orgSlug]/auditoria` muestra lo que se hizo en la organización, de lo más reciente a lo más antiguo: lo que devuelve `GET /api/v1/o/{slug}/audit/` (F2-73), con el cliente generado. Solo lectura.

- **Componente:** `components/audit/audit-list.tsx`, sobre la lista por cursor compartida (ver «Miembros»): su paginación, sus estados y su foco son los mismos.
- **Por fila:** la acción, con su nombre en español y el código debajo; el tipo de entidad y, si la fila la trae, su etiqueta («Sucursal: LIM-01»); quién lo hizo, por tipo de actor («Por: una persona», «el sistema», «un agente de IA», «una integración», «personal de la plataforma») y con la etiqueta del actor si la trae; la fecha y la hora en la zona horaria de la aplicación, con el formato de la configuración regional (12 horas); y el resultado («Correcto», «Denegado», «Falló»; los dos últimos, resaltados).
- **Lo que no se enseña:** `changes` y `metadata` de cada fila, a la espera de la respuesta a OBS-F2-73-1 ([phase-2.md](../docs/phases/phase-2.md)); tampoco identificadores (`id`, `actor_id`, `entity_id`, `correlation_id`), y la API de auditoría no trae el nombre ni el correo de quien actuó: se ven el tipo de actor, `actor_label` si la fila la trae y, para quien puede ver a los miembros, el nombre del directorio (ver «Quién fue»). La API sí devuelve `changes` y `metadata` a quien tiene `audit.view`: la pantalla enseña menos.
- **Nombres:** las acciones salen de `audit.actions.*` en `messages/es-PE.json` (`audit.actions.role.created` para `role.created`) y los tipos de entidad, de `audit.entities.*`. El código viene de la API y se busca por propiedades propias, paso a paso (`lib/message-text.ts`, el mismo lector de los nombres de permisos): una acción o un tipo sin nombre se enseñan con su código, una sola vez. Los tipos de actor y los resultados son enums del contrato y su catálogo está tipado: si el contrato gana uno, no compila hasta darle nombre; uno que esta versión no conoce se enseña con su código (un resultado desconocido, resaltado como los que no son «Correcto»).
- **Una acción nueva en el backend** se ve con su código hasta que se añade su nombre al catálogo.
- **Sin filas:** la pantalla lo dice en lugar de enseñar una lista vacía.
- **Navegación:** la entrada «Auditoría», la última, pide `audit.view`. Es comodidad: quien abre la URL sin el permiso ve el mensaje de «sin permiso» porque la API responde 403.
- **Filtros (F2-76):** tres selectores sobre la lista, «Acción», «Entidad» y «Quién», con «Todas» o «Cualquiera» y lo que la pantalla sabe nombrar (21 acciones, 6 tipos de entidad, 5 tipos de actor; desde F2-83, también las dos acciones de invitación y la entidad «Invitación»). Se aplican al elegir y combinados: envían `action`, `entity_type` y `actor_type` a la API (F2-74). Un selector sin elegir no se envía: la API responde 400 a un filtro vacío. Cada combinación es su propia lista (los filtros van en la clave de la consulta) y se pide de nuevo; «Cargar más» lleva los mismos filtros.
- **Los selectores no se desmontan** mientras la lista filtrada carga, falla o no encuentra nada, y el que se acaba de usar conserva el foco: van en el hueco `controls` de la lista compartida. Tampoco con un 403: la lista se cierra y los selectores siguen ahí, con su foco.
- **Sin resultados con filtros:** «Ningún registro coincide con estos filtros.», distinto del aviso de una auditoría vacía. «Quitar filtros» aparece cuando hay alguno puesto, los quita todos y deja el foco en el primer selector.
- **Lo que los filtros no hacen:** no filtran por una entidad concreta (`entity_id`), ni por una acción o un tipo sin nombre en el catálogo; no hay fecha, resultado ni texto libre; no se guardan en la URL ni entre visitas.
- **Quién fue (F2-77):** con `users.view` según el contexto de la API, la pantalla pide además el directorio de miembros (`GET …/members/`, todas las páginas, `lib/all-pages.ts`) y empareja en el navegador: `actor_id` de la auditoría es el `user.id` del directorio, no el de la membresía. Una fila hecha por una persona del directorio dice «Por: una persona (Ana López)», o su correo si no tiene nombre; `actor_label`, lo anotado en su momento, tiene preferencia. Quien ya no está en el directorio se queda en «una persona». Dos personas con el mismo nombre se leen igual en las filas: las distingue el correo, en el filtro «Persona». Sin `users.view` no se pide nada y no hay nombres: la auditoría no enseña a nadie un nombre que no pudiera ver ya.
- **Filtro «Persona»:** con el directorio cargado, un cuarto selector con «Cualquiera» y cada persona, por orden alfabético, con su nombre y su correo; elegir una envía `actor_id`. La opción lleva el correo y el identificador se busca al enviar: ningún identificador llega al DOM. Quien tiene `users.view` ve los selectores de dos en dos (en una columna en pantallas estrechas), también antes de que llegue el cuarto. Si `users.view` se pierde con la pantalla abierta, el selector y los nombres se van y la lista se vuelve a pedir sin ese filtro.
- **Si el directorio falla o tarda,** la lista funciona igual, sin nombres y sin el selector de persona, que aparece cuando el directorio llega. No se avisa: no es un error de la auditoría. Si lo que falla es volver a pedirlo (al volver a la ventana), siguen los nombres ya leídos y el selector no se desmonta: conserva su foco y lo elegido.

## Seguridad del navegador (F2-07)

Next emite todas las cabeceras de seguridad del HTML; Caddy no añade ninguna.

| Cabecera                                                                                                           | Dónde                                            | Valor                                     |
| ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------ | ----------------------------------------- |
| `Content-Security-Policy`                                                                                          | `src/proxy.ts` (un nonce por petición)           | `src/lib/csp.ts`                          |
| `X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`, `Cross-Origin-Opener-Policy`, `Permissions-Policy` | `next.config.ts`                                 | Fijas                                     |
| `Strict-Transport-Security`                                                                                        | `next.config.ts`, solo en el build de producción | Los valores del backend (`production.py`) |

La política de producción:

```text
default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…';
style-src-attr 'unsafe-inline'; img-src 'self' blob: data:; font-src 'self'; connect-src 'self';
object-src 'none'; frame-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'
```

- **Scripts:** solo se ejecutan los que llevan el nonce de la petición, y los que esos cargan (`'strict-dynamic'`). Sin `'unsafe-inline'` ni `'unsafe-eval'`. Un `<script>` insertado en el HTML, un manejador en línea (`onerror=…`) y `eval` quedan bloqueados.
- **Render dinámico:** Next pone el nonce al renderizar, así que ninguna página se prerenderiza en el build. El layout raíz llama a `connection()`. Efecto medido en el build: `/demo`, `/demo/workspace`, sus 14 módulos y la página 404 eran estáticas y ahora se renderizan en cada petición; `/` y `/o/[orgSlug]` ya eran dinámicas.
- **Excepción documentada:** `style-src-attr 'unsafe-inline'`. `next/image` y los estilos calculados (la altura de una barra) llegan como atributo `style` en el HTML del servidor. Un atributo `style` no ejecuta código y las etiquetas `<style>` siguen necesitando el nonce.
- **Desarrollo (`next dev`):** se añaden `'unsafe-eval'` a los scripts (React lo usa para las trazas) y `'unsafe-inline'` a los estilos. El build de producción nunca los incluye.
- **Sin `upgrade-insecure-requests`:** el stack local sirve HTTP y todas las fuentes son del propio origen. En producción el proxy con TLS redirige y HSTS fija HTTPS.
- **Alcance:** la CSP va en todo lo que responde Next, también en sus páginas 404 y en los estáticos. Solo quedan fuera `/api/` y `/ws/`, que sirve Django. Hoy las páginas de error de Django son HTML estático sin CSP; F2-12 (#59) pasa esos errores a JSON y añade una CSP cerrada a las respuestas de la API.

**Cómo añadir un origen.** Solo si el producto lo necesita y con su motivo en el PR: añadirlo a la directiva más estrecha en `src/lib/csp.ts` (por ejemplo `img-src` para un CDN de imágenes), nunca a `default-src`, y actualizar `src/lib/csp.test.ts`. Un script de terceros recibe el nonce con `<Script nonce>`; no se añade su dominio a `script-src`.

- **Páginas de error propias:** `src/app/not-found.tsx`, `error.tsx` y `global-error.tsx`. Las de serie de Next insertan un `<style>` sin nonce, que la política bloquea. Un módulo desconocido de la demo (`/demo/workspace/x`) responde 404 y muestra la página tras hidratar: al dejar de ser estática, su HTML inicial ya no trae el cuerpo del 404.

Comprobaciones: `src/lib/csp.test.ts` (la política exacta), `src/proxy.test.ts` y `scripts/check-security-headers.mjs`. Este último lo lanza la prueba de humo de la imagen (`SMOKE_CHECK`, en `make check` y en CI) contra el contenedor en ejecución: exige las cabeceras fijas, la CSP exacta y el nonce de la petición en cada `<script>` y `<style>` del HTML, en rutas reales, en la demo y en dos 404. Si cambia la política, cambian `csp.ts` y `csp.test.ts`; el script la toma de `csp.ts`.

Por fila, con `categories.manage` (F3-05b): «Editar» (`CategoryEditAction`: nombre y «Dentro de» en un formulario; envía solo lo que cambió, `parent_id: null` para la raíz y nada si no cambió nada; desactiva ella misma, sus descendientes y los lugares donde la rama pasaría de 5 niveles; `CATEGORY_SLUG_TAKEN` y un 400 de `parent_id` se dicen en el formulario). El resultado lo anuncia el árbol, y un 404 avisa y lo vuelve a pedir (`categories-cache.ts`). La auditoría nombra `category.*` y la entidad «Categoría».
- **Productos (F3-10):** `/o/{org}/catalogo/productos`. `ProductsList` usa `CursorList` sobre `GET …/products/` (por orden de creación): nombre, slug, estado (Borrador, Activo, Descontinuado), tipo (Físico, Servicio) y, si los tiene, marca y categoría. Con `products.manage`, «Crear producto» (`ProductCreate`): nombre, SKU de la variante por defecto (la API lo guarda en mayúsculas), identificador opcional (como en marcas), descripción corta, tipo, y marca y categoría opcionales en `select`, cuyas listas se piden enteras (`everyPage`, el mismo recorrido del árbol de categorías) solo al abrir el formulario; la categoría sigue el árbol con la madre en el texto. La auditoría nombra `product.*` y la entidad «Producto». Cambiar, borrar y las variantes (sus API ya están: F3-06b y F3-07) llegan en otro work item.

- **Almacenes (F3-13):** `/o/{org}/inventario/almacenes`, en el menú como «Inventario» para quien tiene `inventory.view`; la entrada cubre `/inventario/*` y `inventario/layout.tsx` pone encima `InventoryNav` (las pestañas de `SectionNav`, el mismo componente de `CatalogNav`). `WarehousesList` usa `CursorList` sobre `GET …/warehouses/` (por orden de creación, activos o no): nombre, código, sucursal («Sucursal: nombre (código)», solo con `organization.view`: las sucursales se piden enteras con `everyPage`), si está activo, tipo (Tienda, Almacén, En tránsito, Servicio) y si cuenta para la venta. Con `warehouses.manage`, `WarehouseForm`: «Crear almacén» pide código (la API lo guarda en mayúsculas), nombre, sucursal (obligatoria, en un `select` que marca las inactivas; sin la lista no se puede crear y se dice), tipo y si cuenta para la venta, y nace activo; «Editar» en cada fila cambia nombre, tipo, si cuenta para la venta y si está activo, y envía solo lo que cambió: el código y la sucursal no cambian y nunca viajan en el `PATCH`. `WAREHOUSE_CODE_TAKEN` va en el código; un 400 de `branch_id` (ya no existe) en el formulario, y vuelve a pedir las sucursales; un 404 al editar avisa en la lista y la vuelve a pedir. La auditoría nombra `warehouse.*` y la entidad «Almacén». Borrar un almacén (su API ya está, F3-11) llega en otro work item.
- **Existencias (F3-14):** `/o/{org}/inventario/existencias`, primera pestaña de «Inventario» y destino de su entrada del menú. `StockPanel` elige la celda con `useCellPicker` (`cell-picker.tsx`, que el historial reutiliza): el almacén (`select`, marca los inactivos) y la variante, buscando el producto por nombre sin mayúsculas ni tildes entre los que llevan stock (`tracks_inventory`; por SKU todavía no: la lista de productos no trae el SKU de sus variantes); almacenes, productos y variantes se piden enteros con `everyPage` porque la API de productos no busca. Una variante única se elige sola; lo elegido sigue en el `select` aunque la búsqueda ya no lo encuentre. Con almacén y variante, `GET …/inventory/levels/?variant_id=…` da el saldo: existencias, reservado y disponible en el almacén elegido (cero si nunca tuvo movimientos) y en cada almacén con movimientos. Sin almacenes o sin productos que lleven stock, la pantalla dice qué falta con un enlace a donde se crea. Un 403 del inventario cierra la pantalla; uno del catálogo se dice bajo «Producto». Cada lectura que falla se explica por `code` junto a su control, con «Reintentar» (no tras un 403); un 401 lleva al login. Con el almacén elegido (F3-19), debajo, «Todo lo que hay en …»: su stock entero con `CursorList` sobre `GET …/inventory/levels/?warehouse_id=…&has_stock=true` (sin `has_stock` si se marca «Mostrar también las variantes que se quedaron en cero»), por fila el nombre y el SKU de la variante (`variant`, que la API trae con cada saldo), existencias, reservado y disponible. «Ver detalle» (o «Ver y registrar» con `inventory.adjust`) elige esa variante en los controles (`choose` de `useCellPicker`) y lleva el foco a su celda; una variante borrada del catálogo se ve marcada y no se elige. Sin filas, «Este almacén no tiene existencias.».
- **Registrar movimientos (F3-15):** en «Existencias», con `inventory.adjust` y una celda elegida, «Registrar movimiento» abre `MovementForm`: tipo (entrada, salida o ajuste, en radios; entrada al abrir), cantidad (`inputmode="numeric"`; un entero desde 1, desde 0 en un ajuste, hasta un millón: la pantalla lo comprueba con el `valid` nuevo de `FieldsForm` y no envía lo que no lo cumple) y motivo obligatorio. Envía `POST …/inventory/movements/` con una `idempotency_key` de 32 cifras hexadecimales (`crypto.getRandomValues`, que existe también fuera de HTTPS): la clave (de `StockPanel`, así que sobrevive a cerrar el formulario o cambiar de celda) sigue hasta que la API da un movimiento por registrado: tras un fallo de red o del servidor, el siguiente envío lleva la misma aunque se haya corregido algo, y si el primero sí se registró la API lo devuelve (mismos datos, 200) o responde `IDEMPOTENCY_KEY_REUSED` (otros datos): nunca cuenta dos veces. Tras un éxito, o tras `IDEMPOTENCY_KEY_REUSED`, la siguiente es nueva. Sigue «Registrando…» hasta que el saldo vuelve; el historial se marca para volver a pedirse. El resultado se anuncia (`role="status"`, visible) con lo que hay ahora con la celda tal como era al enviar («Entrada registrada: ahora hay 15 de Collar en Central.») y el foco vuelve a «Registrar movimiento». Errores por `code`: `INSUFFICIENT_STOCK` en la cantidad; `WAREHOUSE_INACTIVE` en el formulario; `IDEMPOTENCY_KEY_REUSED` dice que un envío anterior sin respuesta sí se registró, vuelve a pedir el saldo y el historial, y el siguiente envío lleva clave nueva; un 400 de `variant_id` o `warehouse_id` dice que ya no existen y vuelve a pedir almacenes, productos y variantes; sin permiso, red y servidor como siempre. La auditoría nombra `inventory.received`, `inventory.issued` e `inventory.adjusted` y la entidad «Movimiento de inventario».
- **Historial (F3-17):** `/o/{org}/inventario/movimientos`, pestaña «Movimientos». `MovementsHistory` usa `CursorList` sobre `GET …/inventory/movements/` (del más reciente al más antiguo) con los controles de `useCellPicker` en su hueco `controls` (no se desmontan al cambiar de lista); el almacén admite «Todos los almacenes». Sin nada elegido se ve el ledger de toda la organización (F3-19); cada fila nombra su variante («Collar · C-1», y «borrada del catálogo» si ya no está) con el `variant` que trae la API. Los filtros (`variant_id` y `warehouse_id`, los que se hayan elegido) van en la clave de la consulta y viajan con «Cargar más». Por movimiento: tipo (los ocho del contrato, con nombre), motivo, almacén, el cambio con su signo (verde si entra; un lector de pantalla oye «Cambio en existencias»), lo que quedó y la fecha en la zona horaria de la aplicación. Un movimiento registrado en «Existencias» marca el historial para volver a pedirse. Sin filas, «Todavía no hay movimientos con estos filtros.»; un 403 cierra la lista y los controles siguen.
- **Importar stock (F3-22, ADR-028 §5):** `/o/{org}/inventario/importar` (`StockImport`), solo con `inventory.adjust`: sin él dice que no hay permiso y no pide nada; un 403 de la API cierra la pantalla igual. «Descargar plantilla» y, al final, «Descargar filas con error» piden `…/inventory/imports/template/` y `…/{id}/errors/` (CSV, a prueba de fórmulas) y guardan el archivo; un fallo se dice al lado del botón. El archivo (solo CSV; Excel llega con F3-23) se lee en el navegador al pulsar «Previsualizar»: antes de enviarlo se rechazan, con su mensaje, un Excel, más de 1 MiB, uno vacío y más de 1000 líneas con texto (una celda entre comillas con saltos de línea cuenta de más). Viaja en base64 en el JSON de `POST …/inventory/imports/`; un 400 en `content` dice el motivo que escribe la API para quien sube el archivo (la única excepción a no enseñar texto de la respuesta). El archivo no se guarda: ni en el almacenamiento ni en la caché de escrituras (`gcTime: 0` y `reset` al llegar la revisión). La revisión enseña los recuentos (celdas nuevas, cambian, sin cambios, con error), el aviso de archivo ya subido, la codificación de Excel y las columnas ignoradas; «Aplicar N filas» abre una confirmación con el foco en «Cancelar» que dice cuántas celdas cambian, que las filas con error no se aplican y qué es `STALE`. Aplicar (`…/{id}/apply/`) envía una petición por pulsación (`aria-disabled`, Enter mantenido no cuenta) y, sin red, falla enseguida: tras un fallo de red o del servidor se puede volver a pulsar sin miedo, porque la API aplica una importación una sola vez y devuelve el mismo resultado. El resultado cuenta aplicadas, sin cambios, `STALE` y con error. Un 404 vuelve al archivo con su aviso; un 401 lo trata `Providers`. Debajo, en la revisión y en el resultado, «Filas del archivo» (`StockImportRows`, F3-22b) lista cada fila de `…/{id}/rows/`, 50 por página con «Cargar más»: línea, SKU y almacén, el saldo visto y la cantidad nueva (o la cantidad tal como vino si la fila no pasó la revisión; una que falla al aplicar conserva sus cantidades), la acción y sus errores. «Mostrar» filtra con el `?action=` de la API (en la revisión: celdas nuevas, cambian, sin cambios, con error; tras aplicar, también `STALE`); al aplicar la lista se vuelve a pedir y las filas `CREATE` y `UPDATE` salen como «Aplicada». Un fallo se dice con «Reintentar» (al abrir la lista, el foco va a su título); «Cargar más» y «Reintentar» quedan ocupados desde la pulsación hasta la respuesta, también sin red, y la página nueva lleva el foco a su primera fila salvo que ya se haya ido a otra parte, como en la lista por cursor compartida. Un 403 cierra la pantalla, un 401 lo trata `Providers` y una región viva anuncia cuántas filas hay en la lista. La pestaña en el menú del inventario se añade cuando exista su navegación. **Revertir (F3-24):** en el resultado de una importación aplicada que movió alguna celda, «Revertir importación» abre la misma confirmación en línea (foco en «Cancelar»): cuántas celdas vuelven al saldo de antes y que las que cambiaron después quedan `STALE`. Al revertir, recuentos (revertidas, `STALE`, con error), la lista de filas se vuelve a pedir y las que volvieron salen como «Revertida».

## Clientes (Fase 4)

- **Lista (F4-04):** `/o/{org}/clientes`, en el menú como «Clientes» (entre «Equipos» y «Catálogo») para quien tiene `contacts.view`. `ContactsList` (`components/contacts/`) usa `CursorList` sobre `GET …/contacts/` (los del alcance del usuario, por orden de creación): el nombre para mostrar, el teléfono tal como lo guardó la API (E.164) y el correo, si los tiene, cada uno con su nombre para el lector de pantalla; el responsable y la sucursal. Vacío, cargando, error con «Reintentar», «Cargar más» y 403 son los de la lista compartida. En el móvil, una columna; lo largo se parte.
- **Responsable:** «Responsable: tú» si es el usuario (`useTenant().user.id`); con `users.view`, el nombre (o el correo) del directorio (`GET …/members/`, todas las páginas, la misma consulta que la auditoría); si no, o si el directorio falla o se niega, «Responsable: otro miembro», sin aviso. Sin responsable, «Sin responsable». La pantalla no pide nada que el usuario no pueda leer.
- **Sucursal:** «Sucursal: nombre (código)» solo con `organization.view` (las sucursales enteras con `everyPage`, la misma consulta que los almacenes); sin el permiso, o si la sucursal no está en la lista, no se dice nada. Sin sucursal, «Sin sucursal», que se sabe sin pedir nada.
- **Crear (F4-04):** con `contacts.create`, «Crear cliente» (`ContactCreate`, sobre `FieldsForm`): nombre, apellido, nombre para mostrar (opcional: vacío, la API lo forma con los otros dos), teléfono (`inputmode="tel"`; la ayuda propone «+51 987 654 321 en Perú» y no se completa nada: la API exige E.164 y acepta espacios y guiones), correo (`inputmode="email"`), número de documento con su tipo debajo (DNI, carné de extranjería, RUC, pasaporte o «Sin documento») y origen (registro manual, visita a la tienda, recomendación, mensaje recibido o campaña; importación y asistente de IA los pone el sistema). Viaja solo lo escrito, sin espacios exteriores, más el origen elegido. La API pone al usuario como responsable y su sucursal. Un número sin tipo no se envía y se dice junto al número; un tipo sin número lo rechaza la API en `document_type` y se dice también junto al número. Cada campo que la API rechaza (un 400 con su nombre en `fields`) se dice junto a él por el nombre del campo, nunca con el texto de la respuesta (que además no repite el dato); sin ningún nombre, la API responde en `display_name` y se pide un nombre. Un envío por pulsación, Enter mantenido no cuenta, sin red falla y se dice. Sigue «Creando…» hasta que la lista vuelve: el cliente nuevo aparece al final (con «Cargar más», en la última página); se anuncia (`role="status"`, visible) y el foco vuelve a «Crear cliente». Si releer la lista falla, el aviso lo dice. La auditoría nombra `contact.*` y la entidad «Contacto».
- **Editar (F4-05):** con `contacts.update` (cualquier alcance), «Editar» en cada fila (`ContactEditAction`, sobre `FieldsForm`, con los campos del alta salvo el origen): el formulario abre con lo que tenía la fila y, como en almacenes y categorías, viaja solo lo que cambió respecto a lo que había al abrir, más la `version` leída. Vacío borra el dato: el teléfono, el correo y el documento con `null`, el nombre y el apellido con `""`; el nombre para mostrar no se puede dejar vacío. El tipo y el número van juntos: un número sin tipo, o un tipo sin número, se dicen junto al número y no se envían. Sin cambios, «Guardar» cierra sin escribir. **409 `CONTACT_VERSION_CONFLICT`:** sigue «Guardando…» mientras la lista se vuelve a pedir; el formulario se recarga con lo que guardó la otra persona (y su versión) y lo dice en el formulario (`role="alert"`): lo escrito no se envía otra vez solo, el usuario revisa y repite su cambio. Si la lista no vuelve, lo dice y no recarga (un nuevo intento recibiría otro 409, nunca pisa). **404** (ya no está en su alcance de edición, o se borró), también tras un 409 si ya no está en la lista: el formulario se cierra, la lista se vuelve a pedir y lo explica un aviso de la lista (`role="alert"`); el foco va al título si seguía en la fila. Los 400 se dicen junto a su campo por el nombre; un 403, en el formulario. Al guardar, se anuncia («Cliente «…» guardado.») cuando vuelve la lista y el foco vuelve a «Editar». **Casos límite (F4-05b):** lo guardado se escribe en la caché de la lista (con su `version`) antes de volver a pedirla, así que tras «guardado, pero la lista no se pudo actualizar» la fila ya lo enseña y la siguiente edición no recibe un 409 por el propio cambio. Si la lista se relee con el formulario abierto y ya no trae la fila (otra pestaña la borró, o salió de su alcance), la fila sigue en su sitio (`keep` de `CursorList`) con lo escrito y el foco, y el formulario lo dice (`role="alert"`); «Guardar» recibiría el 404 de siempre, y «Cancelar» cierra con el aviso de la lista y el foco en el título. La fila deja de sostenerse al cerrarse el formulario, al borrarla desde su propia fila y si el formulario se desmonta sin cerrarse (la lista se cierra con un 403, o se pierde `contacts.update`): no queda una fila fantasma. Tras un 409 el formulario sigue recargándose con lo nuevo, sin conservar lo escrito (el issue lo deja para cuando lo pida el mantenedor).
- **Borrar (F4-05):** con `contacts.delete`, «Borrar» pide confirmación en la fila con el nombre del cliente y el foco en «Cancelar» (como marcas y categorías). Un envío por pulsación; sigue «Borrando…» hasta que vuelve la lista sin la fila; se anuncia y el foco va al título. Un 404 se explica en la lista como al editar; un 403, en la confirmación, que sigue abierta. Si la lista no se puede releer tras el borrado, la confirmación se cierra igual y el aviso lo dice (con test desde F4-05b). Abrir cualquier formulario o confirmación retira el aviso anterior. El Supervisor de la plantilla (solo `contacts.view`) no ve ninguna de las dos acciones.
- **Ficha (F4-06):** el nombre de cada fila enlaza a `/o/{org}/clientes/{id}`. `ContactCard` lee `GET …/contacts/{id}/`, de solo lectura: el nombre para mostrar como título, una ruta «Good Doggy / Clientes» que vuelve a la lista y una lista de pestañas con solo «Resumen» (notas, etiquetas, oportunidades, cotizaciones, pedidos y reservas se añaden cuando existan sus API; no hay pestañas desactivadas). «Resumen» tiene dos grupos: los datos del cliente (nombre, apellido, teléfono E.164, correo y documento con su tipo, o «Sin registrar» / «Sin documento») y lo de la organización (responsable, sucursal, origen y las fechas de alta y del último cambio, en la zona de la aplicación). El responsable y la sucursal siguen las reglas de la lista, con el mismo gancho (`useContactNames`): «Tú», el nombre del directorio solo con `users.view`, si no «Otro miembro», «…» mientras llega el directorio (el lector de pantalla oye «Cargando»); la sucursal solo con `organization.view` (si no, no se enseña). Un identificador que no es un UUID no se pide. **Un 404** (fuera del alcance, borrado, de otra organización o inexistente: la API no los distingue) es la página de «no encontrada» de cualquier dirección, también si llega con la ficha abierta. Un 403 la cierra como a la lista y un fallo posterior no la reabre; error con «Reintentar» (el foco va al título al abrirse), carga y 401 como en la lista compartida. Al llegar, el foco va al título si no estaba en otra parte: la lista y la ficha comparten el título de la pestaña y Next no anuncia el cambio. La entrada «Clientes» del menú queda marcada en la ficha. Editar y borrar siguen en la lista.
- **Notas (F4-10):** con `contacts.view`, la ficha tiene una segunda pestaña, «Notas» (sin el permiso, solo «Resumen»). Las pestañas siguen el patrón de APG: una sola parada de Tab (la elegida), las flechas, Inicio y Fin mueven el foco y la abren (activación automática), y cada panel queda oculto (`hidden`) mientras no es el suyo. «Notas» se monta la primera vez que se abre y sigue montada al volver a «Resumen» (no se vuelve a pedir). `ContactNotes` lee `GET …/contacts/{id}/notes/` (F4-09) por cursor, de la más reciente a la más antigua, sin reordenar: las fijadas no se adelantan (el cursor de ADR-016 solo ordena por `id`), se marcan con «Fijada» y un borde miel a la izquierda. Cada nota dice su autor con las reglas del responsable (`who` de `useContactNames`: «Tú», el nombre con `users.view`, si no «Otro miembro»; «…» mientras llega el directorio), la fecha de alta (es-PE, hora de Lima) y «editada por …» cuando quien la cambió por última vez (`updated_by_user_id`) no es su autor. El cuerpo es texto: React lo escapa y se respetan sus saltos de línea. Vacía, carga, error con «Reintentar» (ocupado mientras reintenta; el foco va al título «Notas del cliente» al llegar), «Cargar más» (el foco, a la primera nota nueva), 403 (cierra la lista hasta una respuesta buena) y 401 como en la lista compartida; un 404 es el del contacto: la página de «no encontrada», como la ficha. `CursorList` no se usa porque pinta su propia página (título, intro). Añadir (F4-10b) y editar, fijar y borrar (F4-10c) se describen abajo.
- **Añadir una nota (F4-10b, #414):** con `contacts.update` (cualquier alcance; un contacto fuera de su alcance de edición responde 404), «Nueva nota» encima de la lista: un área de texto (16 px, crece con `resize-y`) con la ayuda «Hasta 5000 caracteres», «Fijar la nota» y «Añadir nota». No hay `maxLength` ni se cuenta en la pantalla: la API cuenta caracteres tras NFC, y `maxLength` contaría unidades UTF-16 (cortaría emojis que sí caben); un cuerpo largo o con controles vuelve como 400 en `body` y se dice junto al área, sin repetir lo escrito. Vacía (solo espacios) no se envía y lo dice. Viaja lo escrito sin espacios exteriores y `is_pinned`. Un envío por pulsación (también con Enter o pulsando otra vez enseguida); sigue «Añadiendo…» (área de solo lectura, `aria-busy`) hasta que vuelve la lista con la nota la primera; sin red falla enseguida y se dice; sin sesión (401) sigue ocupado para que el proveedor lleve al login. Al terminar, el formulario se vacía, el foco vuelve al área de texto si no estaba en otra parte y se anuncia «Nota añadida.» (`role="status"` bajo el título de la lista, que se vacía al enviar otra para volver a anunciarse). Si releer la lista falla, la nota entra igual en la caché, la primera, y el aviso lo dice. Los errores, por `code`: 403 «No tienes permiso para escribir notas de este cliente.»; 404 (el contacto salió de su alcance de edición o se borró) lo dice y relee la lista, que lleva a «no encontrada» si el contacto ya no está; un 400 sin `body` es un fallo nuestro. Escribir retira el aviso anterior.
- **Editar, fijar y borrar una nota (F4-10c, #415):** con `contacts.update` (cualquier alcance), las notas propias, y con `contacts.update` `ORGANIZATION` también las de otros (la regla de F4-09), tienen «Editar», «Fijar» (o «Quitar de fijadas») y «Borrar», descritos por su autor y su fecha (`aria-describedby`). Un 404 (la nota se borró, o ya no la puedes cambiar) cierra lo abierto, se explica en la lista (`role="alert"`: «Esa nota se borró o ya no la puedes cambiar…»), las notas se vuelven a pedir y el foco va al título si seguía en la nota. **Editar** abre en la nota el formulario de añadir con lo que tenía (el cuerpo y «Fijar la nota») y «Cancelar»; viaja solo lo que cambió respecto a lo que había al abrir, más esa `version` (aunque la lista se relea debajo); sin cambios, «Guardar» cierra sin escribir. **409 `NOTE_VERSION_CONFLICT`:** sigue «Guardando…» mientras se releen las notas; el formulario se recarga con lo que guardó la otra persona y lo dice; lo escrito no se envía otra vez solo. Si las notas no vuelven, lo dice y no recarga (repetir recibe otro 409: nunca pisa). Al cerrar, el foco vuelve a «Editar». **Fijar** es un `PATCH` con `is_pinned` y la `version`, un envío por pulsación («Guardando…» mientras); su 409 lo explica la lista, que se relee. **Borrar** pide confirmación en la nota con el foco en «Cancelar», un envío por pulsación («Borrando…» hasta que vuelven las notas sin ella); se anuncia y el foco va al título. Un 403 se dice en el formulario, junto a los botones o en la confirmación; sin sesión (401) siguen ocupados. Lo guardado o borrado entra en la caché aunque no se puedan releer las notas (la siguiente edición no recibe un 409 por el propio cambio), y el aviso lo dice. Abrir cualquier formulario o confirmación retira el aviso anterior. Enter mantenido no repite una acción (en el área de texto es un salto de línea). Una nota que desaparece al releer con su formulario abierto se va con él (no se sostiene como en la lista de clientes, F4-05b): guardar recibiría el 404 de siempre.
- **Etiquetas (F4-12, #395):** cada fila lleva sus etiquetas bajo el correo y el «Resumen» de la ficha un grupo «Etiquetas» («Sin etiquetas.» si no tiene), como lista (el lector de pantalla dice cuántas). `TagChip` (`contact-tags.tsx`) escribe siempre el nombre sobre el color de la etiqueta; el texto es negro o blanco, el que más contraste da (`inkOn`, con la luminancia de WCAG): cualquier `#rrggbb` llega al menos a 4,58:1, y un borde la separa del papel cuando el color es claro. Una desactivada sigue en el contacto con «· desactivada» escrito y borde discontinuo. Encima de la lista, «Etiqueta» (un `select` de 16 px y 44 px de alto) filtra con `?tag=`: «Todas las etiquetas» y el catálogo entero (`useTagCatalog`, `GET …/tags/` con `everyPage`, solo con `contacts.view`), con «(desactivada)» en las que lo están, que también filtran. Cada filtro es su propia lista (su clave lleva el filtro) y viaja con «Cargar más»; vacía, «Ningún cliente que puedas ver lleva la etiqueta «…».». Si el catálogo no llega, lo dice bajo el `select` (un 403 sin reintento; otro fallo con «Reintentar») y la lista sigue sin filtro.
- **Poner y quitar etiquetas (F4-12b):** con `contacts.update` (cualquier alcance), el grupo «Etiquetas» de la ficha (`ContactTags`, `contact-tagging.tsx`) tiene «Quitar» junto a cada etiqueta (también las desactivadas; `aria-label` «Quitar la etiqueta «…»», 44 px de alto en el móvil) y, debajo, «Añadir etiqueta»: un `select` con las activas del catálogo que no lleva y «Añadir». Sin elegir no se envía y se dice junto al `select`; sin ninguna por poner, «No quedan etiquetas activas por poner.». `PUT` y `DELETE …/contacts/{id}/tags/{tag_id}/` responden 204 sin cuerpo: la ficha se vuelve a pedir y sigue «Añadiendo…» o «Quitando…» hasta que llega con la etiqueta puesta o quitada; entonces se anuncia (`role="status"`) y, quitada, el foco va al título del grupo si se quedó sin sitio. Si la ficha no vuelve, el aviso lo dice. Un envío por pulsación (una marca, como `FieldsForm`; Enter mantenido no repite); sin red falla y se dice; sin sesión (401) sigue ocupado. Los errores, por `code` (`role="alert"`): 409 `TAG_INACTIVE` nombra la etiqueta y relee el catálogo, que ya no la ofrece; un 404 (el contacto salió de su alcance de edición o se borró) lo explica y relee la ficha, que lleva a «no encontrada» si ya no la ve; 403 «No tienes permiso para cambiar las etiquetas de este cliente.». Sin `contacts.update` las etiquetas solo se ven y el catálogo no se pide.
- **Catálogo de etiquetas (F4-12c):** `/o/{org}/clientes/etiquetas`, una pestaña de «Clientes» (`ContactsNav` sobre `SectionNav`, «Clientes» y «Etiquetas», en la lista y en el catálogo; la ficha no la lleva). Se eligió aquí y no en un «Ajustes» que aún no existe: quien las usa las busca junto a sus clientes, y la entrada del menú (`contacts.view`) ya es la suya. `TagCatalog` (`tag-catalog.tsx`) usa `CursorList` sobre `GET …/tags/`: cada etiqueta como se ve en los clientes y su color en `#rrggbb`. Quien ve contactos lo lee; con `settings.manage` (en `pruebas`, hoy solo el Owner) se crea, se edita y se desactiva o reactiva; sin él, la página dice que solo quien administra la configuración puede cambiarlas. **Crear y editar** (`TagForm`, sobre `FieldsForm`): nombre (hasta 50) y color, que se escribe (`#RRGGBB`, sin espacios exteriores; se envía en minúsculas, como lo guarda la API; otro formato no se envía y se dice junto al campo) o se elige de la paleta del tema (miel, tinta, verde, rojo, gris y gris claro: botones redondos de 44 px en el móvil, con su nombre y su color como `aria-label`, borde de 3:1 como `Choice`; el que coincide con el campo lleva `aria-pressed` y una marca «✓» dentro, distinta del anillo del foco). Una muestra enseña la etiqueta con lo escrito y su texto en negro o blanco. Una nueva empieza en miel. Editar envía solo lo que cambió respecto a lo que había al abrir (el color, comparado en minúsculas), no respecto a la fila que la lista traiga después: si otra persona la renombró mientras tanto, cambiar solo el color no le deshace el nombre. Sin cambios, «Guardar» cierra sin escribir y lo dice. 409 `TAG_NAME_TAKEN` (también frente a las desactivadas) se dice junto al nombre, con el foco en él; un 404 al editar cierra y lo explica la lista, que se relee. **Desactivar y reactivar:** un `PATCH` con `is_active`, un envío por pulsación («Guardando…» hasta que vuelve la lista; Enter mantenido no alterna); se anuncia y el foco se queda en el botón, que pasa a la acción contraria. Un 403 se dice en la fila. Las etiquetas no se borran.
